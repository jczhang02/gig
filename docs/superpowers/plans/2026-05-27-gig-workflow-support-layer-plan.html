阅读结论

这份计划的方向是对的，但边界要比上一版更窄：不要把 gig 做成第二套流程系统，也不要让它碰 Markdown、HTML、索引页或交付归档的内容生产。先把状态、路径、校验、门禁和可自动化输出做成可信底座，其他产物交给 partjob-workflow / agent。

中文评审版

下面不是重新设计计划，而是把更新后的 Markdown 转成更容易审的中文读本。所有技术标识、命令名、JSON 字段、view-model 字段和状态标签都按原计划保留英文。尤其不要把中文叙述误读成要把 gig 的默认输出改成中文。

更正后的职责边界：gig 是账本，不是生产线

用户已经明确纠正：gig CLI 不应该负责生成任何东西。这个边界要放在实现前面，因为它会改掉计划里最容易滑坡的地方。

gig 不生成 workflow 文件；gig 不生成 client-package.zip；gig 只记录、查询、校验、暴露状态。

gig 绝对不做

  • gig 不生成任何 workflow 文件。
  • gig 不渲染、不复制、不刷新 .gig/INDEX.html。
  • gig 不生成 JOB.md、QUOTE.md、PLAN.md、PLAN.html、ACCEPTANCE.md、DELIVERY.md、DELIVERY_*.html。
  • gig 不生成 client-package.zip；package archive 由 partjob-workflow / agent 创建。

gig 只做

  • 记录、查询、暴露 JSON / view-model。
  • 校验路径和文件存在性。
  • 标记 stale / fresh、门禁状态和时间戳。
  • 记录 package metadata，并校验 workflow/agent 已经准备好的 manifest、client dir 和 archive。

partjob-workflow / agent 拥有所有 Markdown、HTML、.gig/INDEX.html 和 package archive 内容。gig 只告诉它们“预期在哪里、现在有没有、状态能不能往前走”。

不能漂移的设计决定

保留 Rust 两层结构

gig-core 继续放 schema、models、repositories、services、路径契约、校验规则和安全检查；gig-cli 继续是薄 clap 壳。不要为了这次重构改写成 TypeScript。

工作流入口在技能层

partjob-workflow 是主流程入口。gig 支持它，不替代它；gig 的输出要稳定到可以被技能、脚本和未来 UI shell 调用。

英文工具契约

命令名、CLI 输出、JSON/view-model 字段、DB enum、状态标签默认保持英文，例如 quote_draft、plan_ready、ready_to_deliver。中文留在 JC 对话和评审页面里。

Phase 1 不做界面

第一阶段不做 TUI / GUI。以后如果要做界面，也只能是薄壳，依赖 gig-core 服务或稳定 --json / view-model 输出。

这份计划最重要的判断：把人类工作流和机器契约分开。JC 读中文、做商业判断；工具层说稳定英文，方便自动化调用。

数据模型与路径边界

计划新增三块核心表，不把所有状态继续塞进旧的 orders。报价前机会、正式项目、交付包记录是三种对象；分开之后，边界才不会被一次“顺手”实现搅乱。

对象用途评审要点
quote_drafts成交前机会、报价区间、XDG 草稿路径、drop/accept 时间线。报价前不能创建正式项目目录；文件由 workflow/agent 准备，gig 记录预期路径并做存在性校验。
order_workflow正式订单的工作流路径、计划审批、验收、交付包引用。不要膨胀 orders；新状态包括 plan_ready、plan_approved、ready_to_deliver。
delivery_packages记录安全客户端包的 manifest、client dir、archive 路径和发送状态。gig 校验并记录已有 archive；不能调用旧的 pack_order(project_dir)，也不能替 workflow 产出 archive。

XDG 与项目内 .gig/

成交前文件只应出现在 XDG quote draft 路径；成交后，正式项目使用项目内 .gig/ 作为工作流约定位置。注意这里说的是“路径契约”，不是文件写入职责。

.gig/INDEX.html 是人看的状态导航页，不是 source of truth。gig 可以记录它的 canonical path，可以暴露状态给 workflow，可以判断它缺失或 stale；内容本身仍归 partjob-workflow / agent。

CLI 与自动化契约

默认人类输出继续英文，短、明确、面向下一步动作。自动化不能解析彩色表格，也不能依赖人类文案；需要稳定 --json 输出和 view-model 字段。

stable machine output
{
  "status": "plan_ready",
  "next_action": "approve_plan",
  "plan_html_path": "/home/jc/dev/partjobs/foo/.gig/plan/PLAN.html"
}

JSON key 和 enum value 不本地化。看板可以给人读，但技能、脚本、未来 UI shell 必须走 --json。

服务层怎么做

服务应该负责不能越界
services::quote记录、更新、查询 quote drafts；保存 workflow 提供的 XDG quote 路径；在转态时检查 quote 文件是否存在；接受或丢弃 quote。不能提前创建正式项目；不能写 XDG 目录或 quote 文件；不能把 Lead order 当成 quote draft。
services::workflow_paths计算 canonical XDG / .gig/ 路径；写入 order_workflow；检查 workflow 创建的文件是否存在；暴露 path/status 给 --json 或 view-model。不能创建 root-level workflow 文件；不能展开、渲染、搬运或刷新 Markdown/HTML 工作流文件。
services::workflow校验状态转移；记录 plan ready、plan approved、acceptance complete、ready to deliver、delivered；在缺路径或缺审批时拒绝推进。不能判断 agent 的工作质量；不能读取任意证据后自己推断验收通过。
services::client_package读取 workflow-created manifest；校验 client-visible 文件位于 .gig/delivery/<date>/client/；校验已有 client-package.zip；记录 metadata。不能调用 pack_order(project_dir)；不能写 manifest；不能创建 archive；不能复制 package 文件。

blocklist 至少要挡住 .gig/、prompts/、internal/、ACCEPTANCE.md、DELIVERY_INTERNAL.html、raw evidence 和内部工作流文件。这里要保守，宁可阻塞也不要泄露。

实施顺序

计划分 11 个阶段。不要一口气改完整条链路；每个阶段都要用失败测试先锁住行为，再实现，再验证。下面的中文读法保留了新的边界：阶段推进可以记录和校验路径，但不能顺手产出工作流内容。

阶段中文读法主要风险
Phase 1V002 schema 与 models：quote_drafts、order_workflow、delivery_packages、orders.project_type。旧订单必须继续可解析。
Phase 2三组 repository：按 id/slug 查 quote draft，更新状态、报价、drop reason、promoted order。repo API 不要偷做服务层决策。
Phase 3XDG quote draft service：记录草稿和预期 quote 文件路径，验证 workflow/agent 已准备的 JOB.md/QUOTE.md。成交前路径一定不能进 /home/jc/dev/partjobs/<slug>。
Phase 4报价接受后创建正式 order，并记录项目本地 .gig/ 预期布局。gig 只能校验 quote 阶段文件已在 .gig/，不能搬运或补写。
Phase 5计划审批流：Accepted -> PlanReady -> PlanApproved -> InProgress。不能绕过 plan_ready 直接执行；也不能在 approve 时处理 .gig/INDEX.html 内容。
Phase 6验收门禁：检查 .gig/acceptance/ACCEPTANCE.md 和证据表。解析不确定时要 fail closed。
Phase 7安全客户端包校验：allowlist/manifest，校验已有 .gig/delivery/<date>/export/client-package.zip。不要调用旧的 pack_order(project_dir)，也不要创建 archive。
Phase 8gig ls 变成英文决策看板，gig ls --json 输出内部状态与下一步动作。人类显示文案不是 API。
Phase 9CLI wiring 与 help text：新 command group、dispatch、英文 examples。不要本地化命令名、JSON key 或 enum。
Phase 10gig show、gig doctor、旧订单兼容。缺 order_workflow 的旧数据不能 panic。
Phase 11README、XDG vs .gig/ 文档、cargo 验证、手工烟测。手工检查 package metadata 和 archive 校验路径，确认没有内部文件泄露。

第一刀怎么切

第一刀要小到能一次打穿，又足够证明新边界：

first implementation slice
V002 schema + quote_drafts + quote record/list/drop

这刀证明成交前 quote draft 住在 XDG，能记录、查看、列出、丢弃，并且不会创建正式项目目录。先把状态、路径和 drop reason 打稳，再进入接受报价后的项目本地 .gig/ 校验。

pre-acceptance: XDG quote draft path post-acceptance: project-local .gig/ no workflow file production

评审提醒

  • Lead / Negotiating 和 quote_drafts 看起来会重叠，但计划要求分开：旧手工流继续兼容，新流在接受前使用 quote_drafts。
  • .gig/INDEX.html 只是状态导航页。不要让 HTML 反向成为数据源，也不要让它替代数据库和服务层校验。
  • 安全客户端包必须基于 allowlist/manifest 校验。blocklist 要拦 .gig/、prompts/、internal/、ACCEPTANCE.md、DELIVERY_INTERNAL.html 等内部材料。
  • 中文可以服务 JC 的阅读和决策，但不能倒灌进 gig 的默认 CLI/status-label 输出。
  • TUI/GUI 可以以后再谈；第一阶段要避免为了未来界面把工作流逻辑拉出 Rust core。
  • 如果某个实现步骤想“顺手补文件”，停下来。那是 partjob-workflow / agent 的活，不是 gig 的活。

完成标准

  • [ ]Quote drafts 住在 XDG；record/list/drop 不提前创建正式项目目录，也不写 quote 文件。
  • [ ]接受报价后，正式 order 记录项目内 .gig/ 预期路径；项目根目录保持只放真实工作文件。
  • [ ].gig/INDEX.html 的路径、缺失和 stale/fresh 状态可被记录或暴露，但页面内容由 workflow/agent 维护。
  • [ ]计划未经显式批准不能执行；状态必须经过 plan_ready / plan_approved。
  • [ ]验收必须有 .gig/acceptance/ACCEPTANCE.md 证据结构，模糊时阻塞。
  • [ ]客户端包只校验和记录已有 manifest、client dir 与 client-package.zip；不能泄露内部文件。
  • [ ]gig ls 对人是英文决策看板，对自动化提供稳定 --json。
  • [ ]旧订单仍能加载和显示；Rust 验证包括 cargo fmt、cargo clippy --workspace --all-targets、cargo test --workspace。
