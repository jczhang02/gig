gig workflow manual / daily cheatsheet

从报价草稿到安全交付的接单工作流

这不是一份命令列表，而是一张工作方式地图：什么时候让外部 workflow 或 agent 产出文件，什么时候让 gig 登记、校验、上传、留痕，以及出错时该先看哪一层。

账本 状态机 校验器 上传留痕 打印速查
一句话边界

gig 负责记录事实、推进状态、验证路径和上传交付物；项目计划、验收材料、客户包内容由外部 workflow 或 agents 生成。把它当作接单工作的「控制层」，不要把它当作内容生成器。

01 / Mental Model

先分清「谁生产内容，谁承认事实」

当前 gig 走的是 workflow-only delivery：CLI 不替你写方案、不替你打包客户文件，也不替你生成验收页。它只在关键门口问一句：文件是否存在、状态是否允许、交付包是否安全、上传是否留下了可追踪记录。

外部 workflow / agents

负责创建项目目录、写 JOB.md、报价页、计划页、验收材料、客户交付内容和最终 zip。

gig CLI

负责 quote draft、订单账本、状态推进、路径记录、文件校验、上传器调用和 delivery artifacts 留痕。

远端服务

S3 uploader 提供文件存储；可选短链接服务把长签名 URL 变成可发给客户的短 URL。

实践判断：如果你正在「创造」内容，应该去找 workflow、agent、编辑器或脚本；如果你正在「确认」某个节点已经发生，才用 gig。这个边界能避免最常见的误用：期待 gig package send 自动生成 client-package.zip。

03 / Quote Draft vs Project Files

XDG 里的报价草稿，不等于项目里的 .gig/

报价阶段还没有正式项目目录，所以草稿只住在 XDG 数据目录；客户接受后，才把外部 workflow 已准备好的项目目录登记进订单。

报价草稿：XDG 数据目录

典型位置是 $XDG_DATA_HOME/gig/quotes/<slug>。这里用于记录报价草稿与价格区间，不创建项目目录，也不生成 .gig/JOB.md。

gig quote new --slug crawler-a --title "数据爬虫" \
  --project-type crawler \
  --summary "采集公开列表并导出 CSV"

gig quote price crawler-a --min 3000 --recommended 5000 --max 8000
gig quote mark-sent crawler-a

正式项目：项目内 .gig/

客户确认后，外部 workflow 应已经建好项目目录和 .gig/ 文件。gig quote accept 只登记这些路径并创建订单；缺文件会阻塞后续 plan、acceptance、package。

gig quote accept crawler-a \
  --project-dir ~/dev/partjobs/crawler-a
记忆法：XDG 是「还没成交的报价记忆」；项目 .gig/ 是「已经成交的交付证据」。不要把草稿目录当项目目录，也不要指望 accept 命令补齐项目文件。

04 / Walkthrough

一单从报价到交付的日常走法

下面的命令用 crawler-a 作为 slug。实际工作中，内容产出发生在外部 workflow；每当你确认一个门槛已经达成，再让 gig 记录它。

1. 报价、定价、标记已发送

gig quote new --slug crawler-a --title "数据爬虫" \
  --project-type crawler \
  --summary "采集公开列表并导出 CSV"

gig quote price crawler-a --min 3000 --recommended 5000 --max 8000
gig quote mark-sent crawler-a
gig quote show crawler-a

2. 客户接受，登记正式项目

# 外部 workflow 已经准备 ~/dev/partjobs/crawler-a/.gig/* 后再执行
gig quote accept crawler-a --project-dir ~/dev/partjobs/crawler-a

gig show crawler-a
gig doctor

3. 计划门：ready 再 approve

# 校验 .gig/plan/PLAN.md 和 .gig/plan/PLAN.html
gig plan ready crawler-a

# 用户或负责人确认计划后
gig plan approve crawler-a
gig work start crawler-a

4. 验收完成，进入可交付

# 可先检查外部 workflow 生成的验收证据
gig acceptance check crawler-a

# 验收材料到位后推进 ready_to_deliver
gig acceptance complete crawler-a

5. 先校验客户包，再发送并变 delivered

gig package check crawler-a \
  --delivery-date 2026-05-27 \
  --delivery-dir ~/dev/partjobs/crawler-a/.gig/delivery/2026-05-27

gig package send crawler-a \
  --delivery-date 2026-05-27 \
  --delivery-dir ~/dev/partjobs/crawler-a/.gig/delivery/2026-05-27

6. 单独发送附件，不改订单状态

gig artifact send crawler-a report.pdf screenshot.png
gig artifact send crawler-a report.pdf --json

7. 收款与归档

gig paid crawler-a
gig archive crawler-a

# 自动修复路径前先看 doctor 输出
gig doctor
gig doctor --fix

05 / File Layout

项目文件和交付目录应该长什么样

路径约定比命令更重要。gig 后续的 plan、acceptance、package 命令都依赖 accept 阶段登记的项目内 workflow 路径。

~/dev/partjobs/crawler-a/ ├── .gig/ │ ├── JOB.md # 外部 workflow 生成：需求与工作边界 │ ├── QUOTE.md # 外部 workflow 生成：报价说明 │ ├── INDEX.html # 项目工作台或索引页 │ ├── plan/ │ │ ├── PLAN.md # gig plan ready 会检查 │ │ └── PLAN.html # gig plan ready 会检查 │ ├── acceptance/ │ │ └── ACCEPTANCE.md # 内部验收材料，不进入客户包 │ └── delivery/ │ └── 2026-05-27/ │ ├── DELIVERY.md # 交付总说明 │ ├── client/ # 只放允许发给客户的文件源 │ │ ├── DELIVERY_CLIENT.html │ │ └── DELIVERY_CLIENT.pdf │ ├── internal/ # 禁止进客户包 │ │ └── DELIVERY_INTERNAL.html │ ├── manifest.toml # client_files 精确白名单 │ ├── export/ │ │ └── client-package.zip │ └── prompts/ # 禁止进客户包 └── src-or-work-files/ # 项目实际工作文件，由外部工具维护
项目层：.gig/JOB.md、QUOTE.md、INDEX.html 是 accept 后的基础事实。缺它们，订单可以存在，但后续 workflow 命令会被路径诊断卡住。
交付层：每次交付单独一个日期目录。客户 zip 固定是 .gig/delivery/<YYYY-MM-DD>/export/client-package.zip，不是随便找一个 zip 上传。

06 / Secure Client Package

客户包先过安全门，再上传

gig package check 是交付前安全门；它只接受外部 workflow 已经创建好的 manifest.toml 与 client-package.zip，并检查 zip 内容是否严格等于白名单。gig package send 只发送匹配的已校验客户包。

manifest 是精确白名单

version = 1
delivery_date = "2026-05-27"

client_files = [
  "README.html",
  "dist/app.zip",
  "screenshots/home.png",
]

zip 里每一个非目录 entry 都必须出现在 client_files。白名单没有写的文件会被拒绝；白名单写了但 zip 缺失也会被拒绝。

目录与路径必须安全

  • delivery_dir、client/、manifest.toml、export/client-package.zip 都必须存在。
  • client/ 和包文件必须留在 delivery 目录内，不能通过 symlink 或路径逃逸。
  • manifest 的 delivery_date 必须匹配命令行的 --delivery-date。
  • zip entry 不能是 symlink，不能使用绝对路径、..、反斜杠或空路径。
会被拒绝的内容原因应该怎么做
.gig/、隐藏路径、以 . 开头的组件内部状态和隐藏文件不属于客户交付物只从 delivery/client/ 复制公开文件
internal/、prompts/包含内部过程、提示词或协作痕迹保留在 delivery 目录内，但不要列入 manifest
.gig/acceptance/ACCEPTANCE.md、internal/DELIVERY_INTERNAL.html验收与内部交付说明不是客户包内容如需客户说明，另写公开版 README 或交付说明页
未列入 manifest 的 zip entry防止临时文件、缓存、草稿被意外打包先更新 client_files，再重建 zip
symlink、绝对路径、../、反斜杠路径防止文件逃逸和跨平台路径歧义使用普通文件和 POSIX 风格相对路径
结果：校验通过后，命令调用配置好的 uploader 上传 zip，写入 delivery_artifacts，把 package 标记为 sent，并把订单推进到 delivered。

07 / Upload + Short Link

短链接是上传器外面的一层包装

当 [delivery.short_link] 启用时，S3 uploader 先生成可分享长链接，随后通过短链接服务换成客户可读的短 URL。不要把真实 token 写进文档、截图或仓库。

[delivery]
default_uploader = "s3:aliyun-hk"

[delivery.short_link]
enabled = true
endpoint = "https://go.jczhang.cc/api/links"
token = "REPLACE_WITH_SHORT_LINK_TOKEN"

[delivery.s3.aliyun-hk]
bucket = "my-bucket"
region = "cn-hongkong"
endpoint = "https://s3.oss-cn-hongkong.aliyuncs.com"
# Optional: enable OSS transfer acceleration/CDN first, then set:
# download_endpoint = "https://oss-accelerate.aliyuncs.com"
access_key = "REPLACE_WITH_ACCESS_KEY"
secret_key = "REPLACE_WITH_SECRET_KEY"
link_ttl_seconds = 604800
path_style = false

请求方式

短链接服务位于 https://go.jczhang.cc/api/links。CLI 使用 Bearer token 调用接口，发送长 URL 和可选 TTL，读取响应里的 short_url。

记录位置

gig package send 与 gig artifact send 最终记录的 remote_url 可以是短链接返回值。Cloudflare Worker 已可用，但本手册只保留占位符，不包含任何真实 secret。

09 / Troubleshooting

常见误区与排查顺序

大多数问题不是命令坏了，而是内容层、路径层、状态层混在一起。先判断是哪一层，再动手。

症状通常原因先做什么
gig plan ready 失败外部 workflow 没生成 .gig/plan/PLAN.md 或 PLAN.html回项目目录补文件，再跑 gig doctor
gig quote accept 后后续命令被挡accept 只登记路径，不会创建 JOB.md、QUOTE.md、INDEX.html让 workflow 生成项目内 .gig/ 基础文件
package send requires ready_to_deliver or revision / client package must be validated before send状态还没到交付门、修订流程没标记 revision，或还没跑 package check先完成 gig acceptance complete，必要时标记 revision，然后运行 gig package check
unsafe package pathmanifest 或 zip entry 有隐藏路径、..、反斜杠、内部目录或禁止文件名清理 client_files，重建 zip
unmanifested package zip entryzip 里出现了白名单之外的文件或目录用 manifest 精确列出客户文件，删除临时文件后重新打包
missing package zip entrymanifest 写了某个文件，但 zip 没有它重建 export/client-package.zip，保持与 manifest 一致
短链接请求失败endpoint、token 或 Worker 响应不符合预期检查 [delivery.short_link]，确认 token 只在本机配置中存在
旧订单 JSON next_action 显示 legacy老数据缺 order_workflow 或 project_type旧订单仍可 list/show/export/archive；需要支持层命令时再补 metadata
artifact send 后状态没变这是预期行为它只上传附件并记录 artifact；客户正式交付仍用 package send

先看状态

gig show crawler-a 告诉你订单在哪一步；状态不对时不要先改文件。

再看路径

gig doctor 会检查 workflow 文件、package artifact 和路径一致性。

最后看上传

只有本地校验通过后，才需要排查 S3、短链接 endpoint 或 token 配置。

这份手册只描述当前已实现的公开命令面。它刻意不包含真实 token、access key 或 secret；复制配置片段时，请只在本机 gig config --edit 中填入真实值。
