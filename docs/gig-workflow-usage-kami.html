从报价到收款：gig workflow 使用手册

这份手册面向日常操作。记住一条边界：gig 是账本、状态机、校验器和客户包上传入口；项目文件、计划 HTML、验收材料和客户交付包仍由外部 workflow / agents 生成。

一句话流程：先用 `gig quote` 记录报价草稿；客户接受后登记已有项目 `.gig/` 文件；再用 `gig plan`、`gig acceptance` 逐关校验；最后用 `gig package send` 校验并上传客户包、收款、归档。

01 · 先分清边界

`gig` 不生成业务材料。它只记录路径、推进状态、校验已有文件、输出下一步动作。

gig 负责

订单账本、报价草稿、状态流转、路径登记、计划/验收/交付包校验、客户包上传留痕、dashboard next action、JSON 输出。

workflow / agents 负责

创建项目目录、生成 `.gig/JOB.md`、`QUOTE.md`、`INDEX.html`、`PLAN.md`、`PLAN.html`、`ACCEPTANCE.md` 和 `client-package.zip`。

不要混用

`gig package send` 是唯一客户交付入口：先校验已有 zip，再通过配置的 uploader 上传并记录 artifact。不再保留绕过上传留痕的兼容交付入口。

lead negotiating accepted plan_ready plan_approved in_progress ready_to_deliver delivered revision paid archived

02 · 第一次使用

先安装 CLI、配置工作目录和渠道。之后 dashboard 才能把订单、报价草稿和下一步动作串起来。

A

安装

cargo install --path crates/gig-cli
B

配置

gig config --edit

至少确认 `dev_root`、`archive_root`、`default_cut_ratio`、`default_currency`。如果要用 `package send` 上传客户包，还要配置 `[delivery] default_uploader` 和对应 uploader。

C

可选：安装 zsh completion

mkdir -p ~/.local/share/zsh/site-functions
gig completions zsh > ~/.local/share/zsh/site-functions/_gig

03 · 支持层 workflow 主线

这是推荐的新流程。所有命令都可以加 `--json` 获取稳定机器可读输出。

1

报价草稿：只记录，不建项目

gig quote new --slug crawler-a --title "数据爬虫" \
  --project-type crawler \
  --summary "采集公开列表并导出 CSV"

gig quote price crawler-a --min 3000 --recommended 5000 --max 8000
gig quote mark-sent crawler-a

此时路径在 XDG 数据目录，例如 `$XDG_DATA_HOME/gig/quotes/crawler-a`。`gig` 不创建项目目录。

2

客户接受：登记 workflow 已生成的项目

gig quote accept crawler-a --project-dir ~/dev/partjobs/crawler-a

外部 workflow 应已准备 `<project>/.gig/JOB.md`、`QUOTE.md`、`INDEX.html`。`gig quote accept` 只登记这些路径并创建 accepted 订单。

3

计划门：ready → approve

gig plan ready crawler-a
gig plan approve crawler-a

# 如果计划要退回修改
gig plan reject crawler-a --reason "补齐风险和验收标准"

`ready` 会校验 `.gig/plan/PLAN.md` 和 `.gig/plan/PLAN.html` 已存在；`approve` 明确把计划从 `plan_ready` 推到 `plan_approved`。

4

开始执行，再做验收

gig status crawler-a in_progress
gig acceptance check crawler-a
gig acceptance complete crawler-a

`acceptance complete` 要求订单已经是 `in_progress`，并通过 `.gig/acceptance/ACCEPTANCE.md` 的证据检查。完成后进入 `ready_to_deliver`。

`ACCEPTANCE.md` 需要包含中文“验收项 / 方法 / 证据 / 结论”，或英文 `item / method / evidence / conclusion`，否则校验会失败。

04 · 安全交付包

客户交付包必须由外部 workflow 创建；`gig` 负责检查白名单、上传 zip、记录 artifact 和推进状态。

禁止把项目根目录直接打包给客户

交付目录应是 `.gig/delivery/<YYYY-MM-DD>/`。客户可见文件放在 `client/`，manifest 写在 `manifest.toml`，zip 固定在 `export/client-package.zip`。

5

manifest 最小形态

version = 1
delivery_date = "2026-05-27"
client_files = ["DELIVERY_CLIENT.html", "DELIVERY_CLIENT.pdf"]

`client_files` 是精确白名单。zip 里不能有未声明文件，不能有反斜杠路径、隐藏路径、`internal/`、`prompts/`、`.gig/`、`ACCEPTANCE.md` 或 `DELIVERY_INTERNAL.html`。

6

默认：校验并上传交付包

gig package send crawler-a \
  --delivery-date 2026-05-27 \
  --delivery-dir ~/dev/partjobs/crawler-a/.gig/delivery/2026-05-27

`send` 会先执行内部严格校验，然后调用 gig uploader 上传 `client-package.zip`，写入 delivery artifact，把 package 置为 `sent`，并把订单推进到 `delivered`。

7

没有兼容交付入口

`gig package send` 是公开命令面里唯一的客户包交付动作。诊断、补录、外部已发送再标记等旧入口已经移除，避免出现没有 gig 上传 artifact 的交付记录。

8

单独文件上传

gig artifact send crawler-a report.pdf screenshot.png

用于临时附件、补充材料或内部沟通文件。它会上传每个文件并写入 `delivery_artifacts`，但不改变订单状态；正式客户包仍走 `gig package send`。

05 · 日常操作看板

你不需要记住每个下一步。`gig ls` 和 `gig show` 会把下一步暴露出来。

看今天该做什么

gig ls
gig ls --json

默认是 workflow decision board。JSON 里有 `quote_items`、`order_items`、`next_action` 和 summary。

看单个订单

gig show crawler-a
gig show crawler-a --json

支持层订单会显示 workflow 路径、项目类型和下一步动作。

检查缺文件

gig doctor

用于发现缺失的 workflow 文件或交付包 artifact。

收款和归档

gig paid crawler-a --amount 5000
gig archive crawler-a

交付后的财务状态仍由原来的订单生命周期管理。

06 · 兼容与迁移

公开交付命令已收敛到 workflow 路径。旧的公开交付入口已移除，不再允许绕过上传留痕。

旧订单兼容

没有 `order_workflow` 或 `project_type` 的旧订单仍可 `list`、`show`、`export`、`archive`。

机器提示

如果某个状态需要 workflow metadata 但旧订单没有，JSON 下一步会显示 `legacy_workflow_metadata_missing`。

统一交付路径

只要你走 `.gig/plan`、`.gig/acceptance`、`.gig/delivery`，统一使用 `quote` / `plan` / `acceptance` / `package send`。单独附件才使用 `artifact send`。

版本语义：本文档描述当前 `gig` workflow 支持层。`gig` 是 ledger / validator，不是文件生成器；生成与渲染由外部 workflow / agents 完成，客户交付上传由 `gig package send` 统一执行并留痕，单独文件上传由 `gig artifact send` 记录到订单。
